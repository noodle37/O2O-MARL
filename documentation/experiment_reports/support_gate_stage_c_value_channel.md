# 队友支持度门控（TCVM）阶段 C：价值记忆通道的受控训练验证（5m_vs_6m）

本报告记录阶段 A 所设计机制在 5m_vs_6m 上的受控在线训练验证。结论是**预先登记的第 4 条分支被触发：价值记忆通道在该预算下整体不成立，该通道被放弃**。报告同时披露一个配置解析缺陷，它破坏了四臂中的一个对照臂；第 4 节说明为什么主结论在该缺陷下依然成立，以及该缺陷意外提供了一个有用的噪声基线。

对应阶段 A 报告：[support_gate_stage_a_premise.md](support_gate_stage_a_premise.md)（动机测量、机制设计与第 7.2 节的预先登记判读表）。

## 1. 实验设置

同一离线检查点 `checkpoints/ovmse_batch_20261014/5m_vs_6m_offline/ovmse_paper_seed1_best.pt` 出发，4 臂 × 3 seed，共 12 条在线微调，每条 20 万步，评测每 1 万步一次、每次 64 局，评测环境种子固定为 424242。除下表所列开关外，配方、预算、探索调度与评测口径完全一致。

| 臂 | 含义 | 开关 |
|---|---|---|
| `none` | 不使用离线价值记忆 | `transfer.mode=full_td`、`use_ovm=false` |
| `ovm` | 不门控的价值记忆（OVMSE 既有调度） | `use_ovm=true`、`support_gate_mode=off` |
| `tcvm` | 仅在执行的联合动作落在旧队友支持域内才保留记忆 | `support_gate_mode=on` |
| `anti` | 同一门控取反，把相当的记忆权重花在相反的步上 | `support_gate_mode=anti` |

θ 由离线数据自身的偏离分位数标定，三个 seed 分别在 13,710 / 13,979 / 14,047 个 filled 步上得到同一个 θ = 1.2149，温度 0.1204 / 0.1229 / 0.1231。θ 不是调出来的常数。

运行脚本 `scripts/run_support_gate_stage_c.sh`，分析脚本 `scripts/analyze_support_gate_stage_c.py`，原始数据 `checkpoints/support_gate_stage_c/5m_vs_6m/*/online.jsonl`。

## 2. 主结果

尾段均值取最后 3 个评测点（约 17.4 万–19.4 万步），所有臂都在同一评测网格上配对。

| 臂 | 回报 终点 | 回报 尾段均值 | 回报 最佳 | 胜率 终点 | 胜率 最佳 |
|---|---|---|---|---|---|
| `none` | 7.89 / 6.19 / 5.90 | 7.89 / 6.26 / 6.40 | 12.815 | 0.000 | 0.312 |
| `ovm` | 0.97 / 1.53 / 1.29 | 1.08 / 1.27 / 1.17 | 12.815 | 0.000 | 0.312 |
| `tcvm` | 0.73 / 1.02 / 0.69 | 0.72 / 1.13 / 0.69 | 12.815 | 0.000 | 0.312 |
| `anti` | 5.20 / 4.91 / 4.73 | 5.26 / 4.95 / 4.90 | 12.815 | 0.000 | 0.312 |

两件事必须先说清楚，否则后面的差值会被误读。

**第一，胜率在该预算下没有分辨力。** 四个臂在 1 万步及之后的每一个评测点上胜率都恰好为 0.000；0.312 这个"最佳"值出现在 t=0，即离线检查点本身。因此本阶段只能用回报判读，胜率不提供任何信息。

**第二，没有任何臂跑过它自己的起点。** 每个臂的"最佳"都等于 t=0 的 12.815。20 万步从该离线初始化出发是一个**整体退化区间**，各臂之间比较的是"塌陷得多深"，不是"最终学到多好"。这与本仓库任务五在 3s5z_vs_3s6z 上的记录一致（无 OVM 臂早期跌到 2.3，到约 180 万–210 万步才反超），即塌陷—恢复的时间尺度在百万步量级，20 万步正落在塌陷谷底。

## 3. 预先登记的判读

阶段 A 报告第 7.2 节登记了四条分支。实际触发的是第四条：

> 若三臂都不及 `none` → 价值记忆通道在该预算下整体不成立，与第 3 节代理口径一致，应放弃该通道。

`none` 的尾段均值 6.85，`anti` 5.03，`ovm`/`tcvm` 约 1.0，三个使用离线价值记忆的臂全部显著低于 `none`，且 3/3 seed 方向一致。按预先登记的判读，**价值记忆通道在该预算下被放弃**，不再对它做调参或扩 seed。

这与阶段 A 的代理口径是同一结论的两次独立到达：阶段 A 在 9 个策略版本上测得逐样本 oracle 门控的收益只有 +0.002~+0.098，而不门控的 OVM 为 −0.670~−4.169，最优常数门控恰为 c = 0.000，即"少用下界"在代理口径下是单调更好；阶段 C 在行为口径上复现了同一单调性。

## 4. 配置解析缺陷，及为什么主结论仍然成立

### 4.1 缺陷

启动脚本用 `system.support_gate_mode=off` 关闭 `ovm` 对照臂的门控。OmegaConf 按 YAML 1.1 解析，把 `off` 判为布尔 `False`；learner 当时用 `str(...)` 接收，得到字符串 `"False"`。判定语句是 `if self.support_gate_mode != "off"`，而 `"False" != "off"` 为真，**于是 `ovm` 臂的门控被静默打开了**。又因为 `"False" != "anti"`，它走的是正常门控分支。

后果：`ovm` 与 `tcvm` 实际上是**同一个配置**。阶段 C 从未包含"不门控的 OVM"这个对照臂，因此 `tcvm − ovm` 这一项无效，必须作废。

缺陷来自运行日志自证：三个臂分别打印 `mode=False`、`mode=True`、`mode=anti`，其中 `False` / `True` 就是被 YAML 吞掉的 `off` / `on`。

### 4.2 为什么主结论不受影响

主结论只依赖"三个用了离线价值记忆的臂是否都不及 `none`"，而 `none` 臂的 `use_ovm=false` 使门控无论取什么值都不会生效（门控只在 OVM 损失分支内乘到 λ 上）。`anti` 臂的字符串是 `"anti"`，未被误解析。因此 `none`、`anti` 两臂的语义正确，`ovm`/`tcvm` 两臂语义相同且都是"开门控的 OVM"。判读所需的三项比较全部成立。

### 4.3 缺陷意外给出的噪声基线

因为 `ovm` 与 `tcvm` 是同一配置，这 6 条运行构成一组**同配置重复实验**，正好度量该设置下的运行间噪声（同 seed 下的差异来自 GPU 非确定性算子）：

| 量 | 值 |
|---|---|
| 6 条同配置重复的尾段回报 | 1.078 / 1.267 / 1.167 / 0.715 / 1.126 / 0.691 |
| 均值、标准差 | 1.007、0.244 |
| 3-seed 均值的标准误 | 0.141 |

这组基线把三项比较放到了可判定的尺度上：

| 比较 | 差值 | 相对 3-seed 标准误 |
|---|---|---|
| `anti` − 开门控 OVM | +4.03 | ≈ 29 |
| `none` − `anti` | +1.82 | ≈ 13 |
| `none` − 开门控 OVM | +5.84 | ≈ 41 |

三项都远超噪声。同时它说明先前读到的 `tcvm − ovm = −0.45` 完全落在同配置噪声内（0.244 的标准差下约 1.8 个标准差），本来就不该被当作效应。

## 5. 为什么门控的方向会是反的：下界幅度与门控位置不可分离

`anti` 稳定优于开门控的 OVM（+4.03，6/6 对 3/3），这不是零结果，而是一个有方向的、远超噪声的信号。它的解释不是"把队友条件取反更聪明"，而是该通道本身有一个结构性缺陷。

价值记忆的生效量是 `[q_off − y]_+`：只有当冻结离线网给出的值高于在线 TD 目标时，`max(q_off, y)` 才真正抬高目标。而 `q_off` 在**离线网自己偏好的动作上最高**，也正是支持度偏离 `D` 最小、门控开得最大的地方。于是：

- `tcvm` 把门控质量集中在高 `uplift` 的步上 → 实际施加的目标抬升最多；
- `anti` 把同样的门控质量放在低 `uplift` 的步上 → `max` 几乎不生效，近似"基本不加下界"；
- `none` 完全不加下界。

三臂的回报正好按"实际施加的下界量"单调排序（1.01 < 5.03 < 6.85），`anti` 的数值落在另两者之间，正是"按施加量插值"的特征。

这暴露了阶段 C 设计上的一个真实缺口：**我匹配的是门控质量（mean gate），而不是下界真正施加的质量。** 阶段 A 的等质量对照是在 gain 口径上匹配的，阶段 C 没有把这一纪律搬过来。由于门控位置与 `uplift` 幅度在该通道内在地相关，"改变位置"必然同时"改变幅度"，因此**价值记忆通道在原理上无法用来检验队友条件假设**——两个因素不可分离。

因此正确的迭代不是把门控符号翻过来（那是在拟合这个混淆），而是换到一个位置与幅度可分离的通道。

## 6. 诊断缺口（已修复）

阶段 C 的日志无法事后审计门控，有两处原因，都已修复并加了回归测试：

1. `run_online` 把每步训练诊断汇总成区间均值时只转发 `train_ovm/` 前缀的键，`support/gate_mean` 被丢弃；汇总又用 `rows[0].keys()` 取键，首行缺键会使整个区间丢键。现改为转发 `train_ovm/` 与 `support/` 两个前缀，并对键取并集。
2. `ovm_target_stats` 收到的是未门控的 `lam` 而不是 `lam_eff`，因此 `lift_effective_mean` 等指标在所有臂上描述的都是"不门控的下界"，两个门控臂的诊断完全相同、无法区分。现改为传入 `lam_eff`，并让该函数接受逐步张量（`lambda_memory` 报告其掩码均值）。

这解释了第 2 节表格之外的一个现象：日志里 `none` 臂的 `lift_effective_mean` 反而最高（1.92~2.22），因为 OVM 关闭时这些指标走的是旁路诊断分支，描述的是"若施加下界会怎样"的反事实，不是实际施加量。

## 7. 回归测试

针对本阶段暴露的缺陷新增 4 项测试（`tests/test_support_gate.py`，全文件 21 项，全仓 179 项通过）：

- `test_yaml_off_token_parsed_as_bool_is_not_treated_as_enabled`：`support_gate_mode=False` 必须归一为 `"off"`，直接钉住 4.1 的缺陷；
- `test_unknown_gate_mode_is_rejected`：未知模式必须抛错，而不是静默当作开启；
- `test_lift_diagnostics_track_the_applied_gate`：门控后的 `lift_effective_mean` 必须小于不门控，`lambda_memory` 必须报告逐步张量的均值；
- `test_gate_stats_survive_the_training_log_filter`：`support/` 键必须能穿过区间汇总。

实现侧把模式解析收敛到 `ovmse/ovm.py::normalize_gate_mode`，它把 YAML 吞掉的 `True`/`False` 映回 `on`/`off`，并拒绝任何其他取值。`training/online.py` 中的标定条件也改为读取 learner 上已归一的模式，不再比较原始配置字符串。

## 8. 结论与下一步

1. **价值记忆通道放弃。** 预先登记的第 4 条分支触发：三个使用离线价值记忆的臂在 3/3 seed 上全部显著低于 `none`，差距为噪声的 13~41 倍。这与阶段 A 的代理口径（最优常数门控 c = 0.000）一致。
2. **该通道无法检验本课题的假设。** 门控位置与下界幅度不可分离（第 5 节），`anti` 优于 `tcvm` 是这个混淆的表现，而不是队友条件方向错误的证据。
3. **队友支持度信号本身没有被否证。** 阶段 A 的测量（`tm_logp_h1` 比等质量常数门控高 +0.2461，95% CI [+0.2292, +0.2615]，两个非队友对照一律不及常数门控）不依赖价值记忆通道，仍然有效。阶段 C 否证的是承载它的通道。
4. **20 万步 / 5m_vs_6m 只能度量塌陷深度。** 任何关于终局性能的主张都不能用该预算得出；但该区间的噪声很小（同配置标准差 0.244），作为"塌陷深度"的判别器是精确的。对于保守项这类以"抑制早期塌陷"为职责的机制，该区间是直接读数而非代理。
5. **下一步：阶段 D，保守项通道。** 把同一个已验证的队友支持度信号改为给 CQL 惩罚**逐样本定位**。该通道没有第 5 节的缺陷：CQL 损失以加权均值归约，按权重重新分布只改变惩罚的位置，总质量由构造保持不变，因此 `uniform`（均匀放置，正是全局 `online_cql_weight` 能表达的部分）就是严格的等质量对照。通道级余量已有记录：PV exp1 中保留在线保守项的臂 B 在 3/3 seed 上比臂 A 高 +0.70。设计与判读见 [support_cql_stage_d.md](support_cql_stage_d.md)。

## 9. 复现方式

```bash
# 训练（每 seed 顺序跑四臂，已达 21 个评测点的会跳过）
bash scripts/run_support_gate_stage_c.sh 1 0
bash scripts/run_support_gate_stage_c.sh 2 1
bash scripts/run_support_gate_stage_c.sh 3 1

# 配对判读（输出预先登记的读数行）
python scripts/analyze_support_gate_stage_c.py \
  --root checkpoints/support_gate_stage_c/5m_vs_6m --tail 3 \
  --out checkpoints/support_gate_stage_c/5m_vs_6m/summary.json

# 回归测试
python -m pytest tests/test_support_gate.py
```

注意：复现本报告第 4 节的缺陷需要缺陷修复前的代码；当前代码中 `normalize_gate_mode` 会把 `support_gate_mode=off` 正确归一为 `"off"`，因此重跑会得到一个语义正确的 `ovm` 对照臂（真正不门控的 OVM）。鉴于第 3 节与第 5 节的结论不依赖该臂，本阶段不重跑。

`scripts/analyze_support_gate_stage_c.py` 的配对逻辑也作了修正：各臂的 `t_env` 会被四舍五入到不同的 episode 边界（如 71753 与 71765），按精确值取交集只会剩下 t=0 一个点，因此改为按评测序号配对，并断言配对点的环境步差不超过 5000。
